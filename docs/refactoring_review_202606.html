1.요약 (Executive Summary)

이 프로젝트는 지주회사의 "상장 자회사 보유지분가치 ÷ 자사 조정시가총액" 비율을 추적하는 정적 대시보드로, common_preferred_spread와 동일한 "GitHub Actions 수집 + 저장소 = DB + GitHub Pages 서빙" 구조입니다. 다중 자회사 스택 차트, 해외 종목 환율 변환(버크셔·애플), 주·야간 세션 인지 스냅샷 보존, SMA250/EMA 추세선과 백분위 통계 등 기능 밀도는 높고, 자매 프로젝트의 일부 문제(캐시 무효화, 장중 워크플로우 동시성)는 이미 개선된 형태로 만들어져 있습니다.

반면 이 프로젝트 고유의 구조적 결함이 명확하며, 핵심은 네 가지입니다: (1) 현재 시점의 지분 구조를 전 기간에 소급 적용해 헤드라인 지표(전체 평균)가 과거 구간에서 최대 5.3배 왜곡됨(실측), (2) 신규 종목 1개만 추가해도 49개 전 종목 히스토리가 그 시점 Yahoo 조정가로 통째로 재작성되는 파이프라인, (3) 27.2MB data.js(이 중 공백 13.5MB)를 매 방문 동기 로드·파싱, (4) 시세 수집의 사실상 전부(49종목 중 48개 실측)가 개인 DDNS의 평문 HTTP 프록시 한 대에 의존 + 테스트 0개·의존성 미고정입니다.

지금 당장 확인이 필요한 사실 (저장소 실데이터로 검증 완료):
① data.js의 세아홀딩스 비율은 2002-07-26에 4,006.44%로 기록되어 있습니다. 자회사로 등록된 세아베스틸지주(001430)는 2022년에 설립된 회사로, 현재 보유주식수 2,214만 주를 20년 전 가격에 소급 곱한 허구값입니다. 이 한 종목 때문에 그날의 "전체 평균"은 682.0%로 기록되어 있으며, 세아를 제외하면 127.9%입니다(5.3배 왜곡). ② 신규 종목 추가는 fetch_data.py의 전체 재빌드를 트리거하므로(2025-05 bio_smart, 2025-12 kpf_tmc 추가 시 최소 2회 발생), 전 종목의 과거 비율이 재빌드 시점의 배당·분할 조정가로 매번 다시 계산됩니다. 대시보드의 과거 값은 고정된 기록이 아닙니다. 상세 경로는 이슈 C1·C2 참고.

잘 되어 있는 점

  • 의존성 제로 프런트엔드 + 풍부한 차트 UX — 다중 자회사 누적(스택) 영역 차트, 데이터줌(드래그·핸들·더블클릭 리셋), SMA250/EMA 오버레이, 백분위 통계 박스, 다크/라이트 테마, iframe 임베드(?embed), URL 상태 공유(?code=).
  • 세션 인지 스냅샷 보존 — fetch_current.py가 KST 주간(kr_day)/미국 야간(us_night) 세션을 판별하고, 같은 세션의 직전 정상값만 재사용(cached_same_session)하며 구성 변경 시 캐시 호환성까지 검사. 스냅샷 버전 단조성 가드(getSnapshotVersion)도 프런트에 있음.
  • 다층 시세 폴백 — 일별: 내부 가격 API → yfinance(청크 → 6패스 개별 재시도 → KS/KQ 접미사 교차 폴백). 장중: KIS Open API → KIS 프록시 → yfinance, 소스 라벨(quoteSource) 추적.
  • 증분 병합과 추세선 증분 재계산 — 마지막 날짜−5일 중첩 재수집, 변경 시작점부터만 SMA/EMA 재계산(trend_recompute_idx), 730일 이전 주간 다운샘플로 데이터 총량 관리.
  • 자매 프로젝트 대비 이미 개선된 점 — data.js에 캐시버스터를 붙이지 않아 브라우저 304 재검증이 동작(전송은 일 1회 ~2.2MB gzip), 장중 워크플로우에 concurrency 그룹 존재, 거대 단일 파일 대신 Python이 4개 파일로 분리.

핵심 권고 (한 줄씩)

  1. Phase 0 (즉시): 데이터 스냅샷 백업 + "신규 종목만 풀 수집" 전환 + 시작일 후퇴 금지 가드 + 의존성 고정 + 워크플로우 공통 동시성. 코드 구조는 건드리지 않고 안전망부터.
  2. Phase 1: validFrom(지분 구조 성립일) 도입으로 허구 구간 제거 + 전체 평균을 중앙값·최소 표본 필터 기반으로 재설계. 헤드라인 지표의 정확성 회복이 이 프로젝트의 최우선 가치.
  3. Phase 2: data.js를 "summary(소형) + 종목별 히스토리(지연 로드)"로 분할 — common_preferred_spread와 동일 스키마 채택으로 공통화 대비.
  4. Phase 3: ES 모듈 분해 + Python/JS 이중 구현 단일화(admin의 holdings 빌더 제거는 반나절) + pytest 회귀 테스트.
  5. 공통화: 양쪽 Phase 0는 즉시 독립 진행, 공통 모듈 추출은 CPS Phase 2 완료 후 두 저장소를 함께 연결한 세션에서. (7장)

3.컴포넌트별 품질 평가

index.html — 대시보드 구조 C+ / 기능 B+

  • 강점 다중 자회사 누적 차트 + 자회사별 기여 툴팁, 데이터줌 패널(포인터 캡처·핸들·팬), 스냅샷 버전 단조성 가드, 가시성(visibilitychange) 인지 자동 갱신, 부분 반영 상태 표기(isPartial·미반영 종목 수). 포맷/계산 순수 함수들은 추출만 하면 바로 테스트 가능한 품질.
  • 약점 약 2,090줄 JS가 하나의 IIFE에 ~90개 함수로 존재. 상태가 최상위 let 10여 개(selectedIdx, periodDays, todayOverviewData…)로 산재하고, 모든 렌더가 innerHTML 전체 재생성 + 리스너 재바인딩(5분 갱신마다 DOM 전체 교체).
  • 약점 차트 x축이 인덱스 균등 간격이라 730일 이전 주간 다운샘플 구간이 일별 구간 대비 시간적으로 5배 압축되어 보임 — "전체" 보기에서 기울기 왜곡(이슈 M4). 100% 기준선을 항상 y축 범위에 포함시켜 영풍(771%) 같은 고비율 종목의 분해능 저하.
  • 사소 renderCards는 escapeHtml 적용, renderTable·툴팁은 미적용(비일관, L1). 캔버스 툴팁 mousemove 전용(터치 미지원). <script src="current.js" onerror=""> 빈 핸들러.

fetch_data.py — 일별 파이프라인 구조 B− / 데이터 무결성 D

  • 강점 다운로드 견고성(청크 → 6패스 개별 재시도 → KS/KQ 접미사 폴백), 다운로드 전멸 종목의 기존 데이터 유지, SMA/EMA 증분 재계산, ISO 주 단위 다운샘플.
  • 약점 신규 종목 감지 시 existing = None 전체 재빌드(이슈 C1) — 전 종목 히스토리가 그 시점 조정가로 재작성되고 내부 API 기여분은 CI에서 소실. 현재 지분 구조의 소급 적용(이슈 C2)과 결합해 과거 기록의 재현성이 없음.
  • 약점 전체 평균이 "그날 데이터가 있는 종목 단순평균" — 최소 표본 필터·이상치 처리 없음(이슈 H2). 다중 자회사 페어는 막내 자회사 상장일로 전체 히스토리가 절단됨(두산 2023-10, HD현대 2024-05, 한화 2024-09 실측 — 의도된 교집합 설계의 부작용).
  • 약점 증분 시작일을 전 종목 최신일 기준 단일값으로 공유(max(last_dates)−5일) → 장기 누락 종목의 갭이 영구화되는 잠재 결함(M5). import 시점 config 로드로 단위 테스트 곤란.

fetch_current.py + price_api.py — 장중 파이프라인 구조 B / 견고성 B

  • 강점 네 파일 중 가장 정돈됨. 세션 판별(kr_day/us_night/offhours)과 같은-세션 캐시 보존, 캐시 호환성 검사(자회사 구성 비교), KIS 토큰 파일 캐시(만료 마진 300초), 소스 라벨링과 부분 반영 메타(preservedPairIds/missingPairIds).
  • 약점 KIS Secrets 미설정으로 실제 운영은 개인 DDNS 프록시가 49종목 중 48개를 전담(현재 current.json 실측) — 가정용 회선·평문 HTTP 단일 장애점(이슈 H3). 프록시 순차 호출 0.7초 간격으로 1회 실행에 ~75초.
  • 약점 current.js와 current.json 동일 내용 이중 생성·커밋(L2). 파일 쓰기가 비원자적(tmp→replace 아님 — CPS는 원자적). cantabile.tplinkdns.com·192.168.68.84 기본값 하드코딩.

admin.html / workflows

C1 — 신규 종목 추가 시 전체 재빌드 (상세)

메커니즘: main()이 config에서 새 pair id를 감지하면(has_new_pair_ids, fetch_data.py:66~74) existing = None으로 만들어(305~307행) 49개 전 종목을 2000-01-01부터 Yahoo에서 재다운로드합니다. admin.html에서 종목 하나만 추가해도("GitHub 저장" → triggerWorkflow()) 이 경로가 실행됩니다.

영향 세 가지:

  • 과거 값의 비재현성 — yfinance auto_adjust=True 가격은 이후의 배당·분할에 따라 소급 변동하므로, 재빌드 때마다 전 구간의 비율 값이 미세하게(배당 누적 구간은 유의미하게) 달라집니다. 증분 모드에서 쌓인 값과 재빌드 값이 혼재하는 이력이 매번 새로 만들어집니다.
  • 내부 API 기여분 소실 — 재빌드는 CI에서 실행되므로 사설 LAN의 내부 가격 API(192.168.68.84)가 공급했던 데이터는 재현 불가. Yahoo 데이터 품질이 나쁜 종목(거래정지·이전상장 이력)은 더 나쁜 데이터로 교체될 수 있습니다.
  • 전체 평균의 소급 변경 — 긴 히스토리를 가진 신규 종목이 들어오면 26년치 평균 곡선 전체가 다시 그려집니다.

발생 빈도(증거): 시작일 분포상 bio_smart(2025-05-15), kpf_tmc(2025-12-15) 추가 시점에 전체 재빌드가 실행된 것으로 확인됩니다. 종목 추가가 일상 운영 행위이므로 "가끔 있는 사고"가 아니라 상시 경로입니다.

수정 방향: ① 신규 pair만 풀 히스토리 수집 + 기존 pair는 증분 유지(다운로드 대상 분리, 부록 8.4 스케치), ② 병합 결과의 pair별 시작일이 기존보다 후퇴하거나 포인트 수가 급감하면 실패 처리하는 가드, ③ 덮어쓰기 전 data.js를 Actions 아티팩트/백업 브랜치에 스냅샷. needs_multi_sub_backfill(51~63행)의 재빌드 트리거도 같은 가드 아래로.

C2 — 현재 지분 구조의 소급 적용 (상세)

증거 (data.js 실측):

날짜항목기록값실제

메커니즘: 비율 = Σ(sharesHeld × 자회사 조정가) ÷ (조정주식수 × 지주사 조정가)에서 sharesHeld·주식수가 모두 "현재" 단일값(config.json)이고 전 기간에 그대로 곱해집니다(fetch_data.py:414, 418). 지분 취득 이전·지주 전환 이전·자회사 설립 이전 구간에도 비율이 생성되며, 이 값이 차트·백분위 통계·SMA250·전체 평균을 오염시킵니다. 다중 자회사 교집합 설계(388행)가 막내 상장일로 히스토리를 절단하는 것(두산·HD현대·한화)은 역설적으로 이 허구를 막는 안전장치 역할을 하고 있으나, 단일 자회사 페어에는 그 방어조차 없습니다.

수정 방향: ① config에 pair 단위 validFrom(현 지분 구조 성립일) 필드를 추가하고 그 이전 히스토리는 생성하지 않음(마스킹) — 가장 적은 비용으로 허구 제거, ② 전체 평균은 validFrom 적용 후 재계산, ③ 장기적으로 자회사별 {from, sharesHeld} 이력 배열로 확장(부록 8.2). 세아·티와이 등 분할/전환 종목의 validFrom을 우선 채우는 것만으로 헤드라인 지표가 정상화됩니다.

H1 — 27.2MB 초기 페이로드 (상세)

data.js는 indent=2 직렬화로 27.2MB이며(콤팩트 직렬화 시 13.7MB — 13.5MB가 공백), <script src="data.js"> 동기 로드라 첫 화면이 전체 파싱을 기다립니다. 캐시버스터가 없어 둘째 방문부터는 304로 전송이 절약되는 점은 CPS보다 낫지만(전송 ~2.2MB gzip/일), 파싱 비용 27.2MB는 매 방문 발생하고, 사용자가 차트로 보는 건 한 번에 1종목입니다.

  • 즉효(반나절): json.dumps(..., separators=(",", ":")) — 27.2→13.7MB(−50%). 파싱 시간도 절반 수준으로.
  • 근본(Phase 2): "메타+현재가" 소형 summary와 pair별 컬럼형 히스토리 분리 + 지연 로드 — 초기 수백 KB. CPS Phase 1과 동일 스키마로 맞추면 공통 로더를 공유(부록 8.2).

H2 — 전체 평균 지표의 통계적 취약성 (상세)

"전체 평균"은 그날 데이터가 존재하는 종목들의 단순평균입니다(fetch_data.py:555~571). 구성 종목 수가 2000년 5개 → 2010년 15개 → 2020년 34개 → 현재 49개로 변해 장기 곡선의 수준 변화가 상당 부분 구성 효과이고, 최소 표본 필터가 없어 초기 구간은 5~10종목 평균이며, 동일가중이라 영풍(771%)·세아(194%, 과거 허구 4,006%) 같은 꼬리값이 평균을 지배합니다. C2 수정(validFrom) 후에도 남는 문제이므로 별도 이슈로 분리했습니다. 장중 평균(build_average_entry)도 같은 단순평균이라 방식 자체는 배치와 일관되며(CPS의 H4 같은 방식 불일치는 없음), 재설계 시 양쪽을 함께 바꾸면 됩니다.

  • 권고: 평균과 함께(또는 대신) 중앙값을 기본 지표로, 구성 종목 N≥20 미만 구간은 표시 제외(또는 음영 처리), 카드에 "N종목 기준" 표기는 이미 있으므로 차트에도 구성 변화 주석 추가.

H3 — 단일 개인 프록시 의존 (상세)

현재 current.json 기준 49종목 중 48개의 quoteSource가 kis_proxy, 즉 http://cantabile.tplinkdns.com:3288(가정용 DDNS, 평문 HTTP) 한 대가 10분마다 전 시세를 공급합니다. KIS Open API 직접 호출 경로는 구현되어 있으나 Actions Secrets(KIS_APP_KEY/SECRET) 미설정으로 비활성 상태입니다. 프록시가 내려가면 yfinance 지연 시세로 강등되고, 공개 저장소에 개인 엔드포인트가 노출되어 있습니다(price_api.py의 LAN IP 포함). 권고: Secrets 설정으로 KIS 직접 호출을 1차로 승격 + 프록시는 폴백으로 강등, 엔드포인트 기본값은 코드에서 제거(환경변수 필수화).

6.추가 기능 제언

가치 = 투자 판단 기여도 × 구현 난이도 대비. 데이터가 이미 갖춰진 항목부터 정렬. (#)는 CPS 제언과 공통 — 공통 모듈로 한 번 만들어 양쪽에 적용 가능.

#기능노력설명 / 근거
1비율 통계 밴드 (z-score/백분위 오버레이) (#)M백분위 숫자는 이미 통계 박스에 있음 — 차트에 ±1σ·2σ 밴드와 1y/3y 백분위 칩을 얹어 "지금 역사적으로 싼 구간인가"를 시각화. 추가 수집 불필요.
2자회사 기여 분해 패널S스택 데이터가 이미 히스토리에 있음(subsidiaries[].ratio). 기간 선택 시 비율 변화를 자회사별 기여로 분해한 표/바 — "이번 달 비율 확대는 한화에어로 때문" 류의 직답.
3임계 알림 (#)Mfetch_current 말미에 비율/백분위 임계 교차 시 Telegram 발송. 10분 주기 인프라 재활용이라 추가 비용 0. 임계값은 config 확장.
4자매 대시보드 교차 연동S같은 그룹사의 우선주 괴리율(CPS)과 지주사 비율을 상호 링크/임베드(?embed 이미 지원). 두 프로젝트가 연결된 자산임을 사용자 가치로 전환하는 가장 싼 방법.
5지분 변동 이력 + 공시 마커LPhase 1 validFrom의 확장. 지분 추가 취득/처분 시점을 차트 마커로 — 비율 점프의 원인(가격 vs 지분 변동) 구분 가능.
6전 종목 히트맵/산점도 뷰 (#)Mx=조정시총, y=백분위(z-score), 색=당일 변화 — 49쌍 비교 한 화면. 카드 그리드보다 스크리닝에 적합.
7평균회귀 백테스트 (analysis/) (#)LCPS의 analysis/ 프레임(현실적 수수료·정수 주식 가정) 이식: "백분위 하위 X% 매수 → 중앙값 회귀 매도" 전략 검증. validFrom 정리(Phase 1) 이후에 해야 의미 있음.
8관심종목 핀 + 상태 보존 (#)S즐겨찾기 핀, 기간/정렬 선택 localStorage 보존.
9CSV/JSON 내보내기 (#)S선택 종목 히스토리 다운로드 — 데이터는 이미 클라이언트 메모리에 있음.
10모바일 터치 + PWA (#)Mtouchmove 툴팁, 매니페스트+서비스워커(stale-while-revalidate). Phase 2 분할 이후 적용해야 효과적.

7.3 권장 진행 순서

  1. 즉시, 각자: 양쪽 Phase 0(안전망)는 의존성이 없으므로 병렬 진행. HV는 C1 가드·validFrom(Phase 1)까지 단독으로.
  2. CPS Phase 1~2 완료 → 데이터 스키마·프런트 모듈 경계가 실물로 확정됨.
  3. HV Phase 2~3을 그 스키마·경계에 맞춰 정렬 (본 보고서 부록이 이미 호환 설계).
  4. 공통 모듈 추출: 두 저장소를 함께 연결한 세션에서 진행 (한쪽만 보며 추상화하면 다른 쪽에 안 맞는 인터페이스가 나옴). 공유 방식은 ① 별도 저장소 + 복사 동기화(가장 단순) ② git submodule ③ npm 패키지(빌드 도입 후) 순으로 검토 — CPS 보고서와 동일 결론.
